# Purpose and System Overview
This document is the Software Requirements Specification for SitNeat. It tells you what the app must do and how I will test it. The PRD explained why we are building this app. This document turns those goals into clear rules. The TDD will explain how the app is actually built. SitNeat is a web app for one restaurant. The frontend is built with React.js and TypeScript. The backend is built with Python and FastAPI. PostgreSQL stores all the data. The backend serves REST APIs. It checks every request and makes sure only the right people can do the right things.

# Terms and User Roles
A seat is a bookable table with its own number and capacity. A reservation is a booking for one seat, one group of people, and one time period. RBAC means role based access control. In simple words, your role decides what you are allowed to do. A security scope is a named permission that an API needs before it will work. An ownership check means a customer can only see their own bookings. The MVP is the smallest complete version of the app for this course.

There are three roles. A customer is a normal person. They can register, log in, view their profile, check which seats are free, and create, view, edit, or cancel their own bookings. They cannot see anyone else's bookings and they cannot use staff or manager tools. A staff member is a restaurant worker. They can see today's bookings, read the food and allergy notes, update allowed statuses, and cancel a confirmed booking if a guest asks. They cannot manage accounts, roles, seats, or settings. A manager is the boss. They can see and filter all bookings, manage seats and staff, change settings, update statuses, and view simple summary counts. A manager cannot create or promote other managers through the app.

One important rule is that public sign up always creates a customer. The backend never trusts a role or a customer ID that the browser sends. Staff accounts are created by a manager. Manager accounts are set up outside the normal app.

# Authentication Requirements
FR-AUTH-001 says visitors can register with their full name, email, and password. FR-AUTH-002 says public sign up always creates a customer, and if someone tries to sneak in a different role, the system ignores it. FR-AUTH-003 says active users can log in with email and password. FR-AUTH-004 says the system rejects wrong passwords, inactive accounts, and missing or expired tokens. FR-AUTH-005 says passwords are stored as secure hashes, never as plain text. FR-AUTH-006 says a logged in user can view their own profile and the frontend has a logout button. FR-AUTH-007 says only a manager can create, activate, or deactivate staff accounts.

# Seat Requirements
FR-SEAT-001 says a manager can create seats with a unique seat number, capacity, optional description, and an active flag. FR-SEAT-002 says a manager can update a seat's number, capacity, description, or active flag. FR-SEAT-003 says seat capacity must be a positive number between one and twenty. FR-SEAT-004 says inactive seats are not offered for new bookings and cannot be picked during a booking change. FR-SEAT-005 says the seat list shows active seats, and managers can ask for inactive seats when they need to manage them. FR-SEAT-006 says availability search takes a date, a start time, and a party size, and then applies restaurant hours and booking rules. FR-SEAT-007 says availability results show the seat ID, seat number, capacity, description, and whether it is free.

# Reservation Requirements
FR-BOOK-001 says a customer can create a reservation for one active seat and a valid time slot. FR-BOOK-002 says the backend works out the end time using the restaurant's configured duration. FR-BOOK-003 says the system checks capacity, availability, opening hours, and booking rules again when creating or changing a reservation. FR-BOOK-004 says a booking that saves successfully is confirmed straight away. FR-BOOK-005 says the system stops two people from booking the same seat at overlapping times, even if they click at the same moment. FR-BOOK-006 says customers can only list and view their own reservations and history. FR-BOOK-007 says customers can change their own confirmed booking only before the cutoff time. FR-BOOK-008 says customers can cancel their own confirmed booking only before the cutoff time. FR-BOOK-009 says a change is rejected if the new seat or time is not available or if a booking rule fails. FR-BOOK-010 says cancelling a confirmed booking frees the seat for that time.

# Food and Allergy Requirements
FR-FOOD-001 says every reservation must have a food preference of vegetarian or non-vegetarian. FR-FOOD-002 says every reservation must also have an allergy declaration of no known allergies or allergies specified. These are two separate things. FR-FOOD-003 says allergy details are required and have a length limit when allergies specified is picked. FR-FOOD-004 says food preference and allergy declaration are stored separately. FR-FOOD-005 says allergy details are only visible to the customer who owns the booking, authorized staff, and managers.

# Staff Requirements
FR-STAFF-001 says staff can see confirmed and seated reservations for today. FR-STAFF-002 says staff can move a booking from confirmed to seated and from seated to completed when the rules allow it. FR-STAFF-003 says staff can cancel a confirmed booking on a guest's behalf. FR-STAFF-004 says staff cannot manage accounts, roles, seats, or restaurant settings.

# Manager Requirements
FR-MGR-001 says a manager can view and filter all reservations by date and status. FR-MGR-002 says a manager can create, update, activate, and deactivate seats. FR-MGR-003 says a manager can create and update staff accounts and activate or deactivate staff. FR-MGR-004 says a manager can set opening hours, reservation duration, slot interval, minimum lead time, advance booking window, and customer change cutoff. FR-MGR-005 says a manager should be able to see total reservations and counts by status for a chosen date range. FR-MGR-006 says staff management endpoints cannot create, promote, or demote manager accounts.

# Role and Security Requirements
FR-ROLE-001 says every protected API checks permissions on the backend. FR-ROLE-002 says the backend checks reservation ownership by itself, and it does not rely on the frontend. FR-ROLE-003 says customers cannot set the customer ID, role, status, end time, or any other field that only the server should control. FR-ROLE-004 says if a customer tries to open another customer's reservation, they get a not found response with no details. FR-ROLE-005 says users cannot give themselves extra permissions or change their own role.

# Business Rules and Status Flow
BR-01 says the MVP supports one restaurant and one time zone. BR-02 says each reservation uses one seat, and the party size must be at least one and no bigger than the seat's capacity. BR-03 says the end time equals the start time plus the configured duration, and the customer does not send the end time. BR-04 says a seat must be active and free for the whole booking time. BR-05 says confirmed and seated reservations block overlapping bookings on the same seat. BR-06 says a new booking is confirmed immediately, and there is no pending status. BR-07 says the allowed flow is confirmed to seated to completed, and confirmed can also become cancelled. BR-08 says completed and cancelled are final, and seated bookings cannot be cancelled in the MVP. BR-09 says customer changes and cancellations must happen before the cutoff, and staff or managers can cancel a confirmed booking on a guest's behalf. BR-10 says allergy information is declared by the customer, and SitNeat does not guarantee allergen free food.

# REST API Requirements
All paths start with slash api slash v1. JSON is used for the request and response bodies. Protected routes need a valid access token and the right scope. The backend also checks the user's role and whether they are allowed to touch that record. There is a public endpoint to register a new customer account and it returns 201. There is a public endpoint to log in and it returns 200. There is a logged in endpoint to read the current profile and it returns 200. There is an endpoint to list seats that needs the seats read scope and it returns 200. There is an endpoint to search availability that needs the seats read scope and it returns 200. There is an endpoint to create a seat that needs the seats manage scope and it returns 201. There is an endpoint to update a seat that needs the seats manage scope and it returns 200. There is an endpoint to read restaurant settings that needs the settings read scope and it returns 200. There is an endpoint to update settings that needs the settings manage scope and it returns 200. There is an endpoint to create a reservation that needs the reservations create own scope and it returns 201. There is an endpoint to list your own reservations that needs the reservations read own scope and it returns 200. There is an endpoint to read one reservation that needs the right role or scope plus an ownership check and it returns 200. There is an endpoint to edit an eligible own booking that needs the reservations update own scope and it returns 200. There is an endpoint to cancel an eligible confirmed booking that needs own or operational permission and it returns 200. There is an endpoint to update an allowed status that needs the reservations update operational scope and it returns 200. There is an endpoint to list today's operational bookings that needs the reservations read operational scope and it returns 200. There is an endpoint to list and filter all bookings that needs the reservations read all scope and it returns 200. There is an endpoint to create a staff account that needs the staff manage scope and it returns 201. There is an endpoint to list staff accounts that needs the staff manage scope and it returns 200. There is an endpoint to update, activate, or deactivate staff that needs the staff manage scope and it returns 200. There is an endpoint to read date range counts that needs the reports read scope and it returns 200. There is a public health check endpoint that returns 200.

# Data Requirements
The user entity has fields like ID, full name, normalized email, password hash, role, active flag, and timestamps. Email must be unique. Role is customer, staff, or manager. Password is never stored as plain text. The seat entity has fields like ID, seat number, capacity, optional description, active flag, and timestamps. Seat number must be unique. Capacity is between one and twenty. Inactive seats cannot be booked. The reservation entity has fields like ID, customer ID, seat ID, start and end timestamps, party size, food preference, allergy declaration and details, status, and timestamps. Every reference must exist. The end time must come after the start time. The party must fit the seat. The status must be one of the four allowed values. The restaurant settings entity has opening hours, duration, slot interval, minimum lead time, advance booking window, change cutoff, and time zone. Values are checked, and new settings apply to later bookings. Use primary keys, foreign keys, unique constraints, and validation checks. Add indexes for common searches by customer, seat, start time, and status. Use a database transaction and a safe constraint or locking strategy to prevent double booking. Store timestamps in a consistent way and use the restaurant time zone for opening hours and daily staff lists.

# Security Requirements
SEC-01 says hash passwords with a well maintained algorithm like Argon2id or bcrypt. SEC-02 says sign access tokens, set an expiry, and check them on every protected request. SEC-03 says keep signing secrets and database credentials out of source control. SEC-04 says enforce scopes and roles on the backend, because frontend guards are not real security. SEC-05 says check reservation ownership and never trust a customer ID that the browser sends. SEC-06 says only a manager can manage staff accounts or restaurant settings. SEC-07 says check the request data and return safe error messages. SEC-08 says never log passwords, tokens, database secrets, or full allergy details. SEC-09 says allow only the approved frontend origin through CORS in deployment. SEC-10 says use HTTPS in deployment, and if you use cookies you need CSRF protection, and if you use bearer tokens you must store them carefully. SEC-11 says only the customer, authorized staff, and managers can see allergy data. SEC-12 says log important manager actions without storing sensitive details.

# Non Functional Requirements
NFR-01 says forms have clear labels and helpful errors, and pages show loading, empty, success, and failure states. NFR-02 says core navigation and forms work with a keyboard and have accessible labels. NFR-03 says for the course demo, normal read requests should usually finish within two seconds on the development setup, not counting a slow network. NFR-04 says the database prevents overlapping active bookings on the same seat, even when requests come in at the same time. NFR-05 says separate the API routes, schemas, business logic, and database models into clear modules. NFR-06 says support recent versions of the main desktop and mobile browsers. NFR-07 says collect only the information you need, restrict allergy details, and decide how long to keep data. NFR-08 says the repository includes setup instructions, an environment example, API docs, the PRD, the SRS, and the TDD. NFR-09 says automated tests cover booking rules, authentication, roles, ownership, and status changes. NFR-10 says the API URL, database connection, signing secret, and restaurant settings can be changed without touching the code.

# Error Handling
Errors should use the same JSON shape every time, with a stable code and a short message. For example, if someone else books the seat before the customer submits, return HTTP 409 with the code SEAT UNAVAILABLE. Field errors should tell the user what to fix. Unexpected errors are logged with a request ID, but stack traces, credentials, and database details are never sent to the browser.

#Main Use Cases
UC-01 is register. A visitor enters name, email, and password. The system checks the details and creates a customer account. A duplicate email shows a clear error. UC-02 is log in. A user enters their credentials. The system checks the password and account status and then returns a token and safe profile details. Wrong credentials give a generic error. UC-03 is check availability. A user picks a date, start time, and party size. SitNeat checks hours, booking limits, seat capacity, and existing bookings and then returns suitable seats. UC-04 is book a seat. A customer picks a seat and enters food and allergy details. The system checks again and saves a confirmed booking, or returns a conflict if the seat is gone. UC-05 is change or cancel. A customer changes or cancels their own confirmed booking before the cutoff. The system checks ownership, cutoff, capacity, and availability. UC-06 is staff operations. Staff view today's bookings, check the allowed details, update the status, or cancel a confirmed booking on a guest's behalf. UC-07 is manager operations. A manager manages seats and staff, changes settings, filters bookings, and views summary counts.

# Acceptance and Test Plan
T-01 says register with the role set to manager and the account is created as customer only. T-02 says log in with a wrong password or an inactive account and access is denied safely. T-03 says call a protected API without a valid token and the API returns 401. T-04 says customer A asks for customer B's booking and the API returns 404 without revealing details. T-05 says a customer tries to manage staff or seats and the API denies it. T-06 says the party size is bigger than the seat capacity and the request is rejected. T-07 says a customer books an inactive seat and the request is rejected. T-08 says two overlapping requests try to book the same seat and at most one succeeds while the other gets a conflict. T-09 says allergies specified is picked but the details are blank and the request is rejected with a field error. T-10 says a customer tries to edit or cancel after the cutoff and the request is rejected. T-11 says someone tries to jump from confirmed straight to completed and the request is rejected. T-12 says staff try to change restaurant settings and the API denies it. T-13 says a manager changes opening hours or duration and the valid settings are saved and applied to future bookings. T-14 says an unexpected server error happens and the response does not leak stack traces or secrets. Use backend unit tests, API integration tests, authorization tests for all three roles, PostgreSQL tests for booking conflicts, and frontend tests for forms and error states. Add an end to end booking test if there is time.
