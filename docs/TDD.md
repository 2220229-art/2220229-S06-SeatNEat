# Purpose
This document is the Technical Design Document for a project called SitNeat. It explains how I plan to build the app. It covers the architecture, the database, the API contracts, the security model, the booking rules, the testing approach, and the deployment plan. This is a design plan and not proof that the app is already built or tested. It is written for my course assessor and anyone who wants to understand how SitNeat will work under the hood. I kept the language simple so it is easy to follow even if you are new to web development.

# Introduction and Scope
SitNeat is a small web app for one restaurant. Customers can reserve seats online and the restaurant can manage those reservations. This TDD turns the product behavior from the PRD and SRS into a real technical plan using React with TypeScript, FastAPI, and PostgreSQL.

The MVP scope includes customer registration, login, profile viewing, and own reservation management. It includes seat listing and availability search by date, time, and party size. It includes reservation creation, allowed edits, cancellation, and status changes. It includes food preference like vegetarian or non vegetarian and customer declared allergy information. It includes staff operational views and status updates. It includes manager tools for seats, staff, hours, and simple summaries. The backend enforces authentication, role permissions, security scopes, ownership checks, validation, and conflict safe booking.

The out of scope list includes online payments, food delivery, inventory, loyalty programs, chat, AI, machine learning, recommendations, and third party booking integrations. It also excludes multi branch restaurant administration, advanced analytics, and a native mobile app. SitNeat does not give medical advice, allergy diagnosis, or a guarantee that food is allergen free.

Some assumptions are that the MVP serves one restaurant location with one time zone. Public registration creates customer accounts only. Staff accounts are created by manager authorized workflows. The reservation duration is configurable by the manager with a simple default like ninety minutes. All dates and times are validated on the backend. The database stores timestamps in a consistent way, preferably with timezone awareness.

# Architecture Overview
Think of SitNeat like a restaurant. There is the dining area where customers sit and interact. There is the kitchen where all the work happens. And there is the storage room where ingredients are kept. My app works the same way. The frontend is the dining area, and it is built with React and TypeScript. The backend is the kitchen, and it is built with FastAPI and Python. The database is the storage room, and it is PostgreSQL.

I use a modular monolith, which means one frontend, one backend, and one database. The browser talks to the backend through versioned JSON REST APIs. The backend handles business rules, access control, and data integrity. The frontend makes things easy to use, but it is not a security boundary.

When a request comes in, the user interacts with a React page or form. The frontend does basic validation and sends an HTTPS request to slash api slash v1. FastAPI checks the request using Pydantic models. Authentication dependencies check the access token and load the current user. Scope dependencies and service level ownership checks authorize the action. The service applies business rules and uses a database transaction when needed. SQLAlchemy saves or reads data, and PostgreSQL constraints provide the final layer of protection. The API then returns a documented success response or a consistent error response.

My design principles are simple. Keep HTTP routing separate from business logic. Use clear request and response schemas and do not return database objects directly. Enforce permissions in the backend for every protected operation. Use database constraints and transactions for rules that must stay true even when two requests come in at the same time. Keep the first release small and easy to observe, and avoid unnecessary abstractions.

# Technology Decisions
I chose React with TypeScript because it gives me a typed and interactive user interface. It is great for role based dashboards. I use React Router for client side navigation, and the route guards are only for user experience and not for real security.

I chose FastAPI because it gives me Pydantic validation, dependency injection, OpenAPI documentation, and OAuth2 security utilities out of the box. I chose PostgreSQL because it supports transactions, foreign keys, constraints, and exclusion constraints for booking conflicts. I use SQLAlchemy as the database ORM for maintainable queries and clear transaction boundaries. I use Alembic for version controlled database migrations. I use JWT access tokens for stateless bearer token validation with short expiry. I use Pytest for backend tests and Vitest with React Testing Library for frontend tests.

There are some trade offs. A modular monolith is easier to run and assess than microservices. JWT bearer authentication is straightforward for an API course project, but token storage needs care. If I keep tokens in memory, a page refresh may require reauthentication unless I add a refresh strategy. If I put tokens in cookies, I need cookie flags and CSRF protection. I must choose one strategy and document it consistently.

# Application Structure
My repository has a frontend folder and a backend folder. The frontend folder has a source folder with subfolders for API calls, reusable components, authentication context, hooks, layouts, pages for customer, staff, and manager, route configuration, shared TypeScript types, and utility functions. The backend folder has an app folder with subfolders for API version one routes, core configuration and security, dependencies for current user and scopes, database models, Pydantic schemas, business services, optional repositories, and the main entry file. There is also an Alembic folder for migrations, a requirements file, an environment example file, a docs folder with the PRD, SRS, and TDD, and a readme file.

The backend modules have clear responsibilities. The API version one folder handles HTTP routes, status codes, dependency declarations, and request and response binding. The schemas folder holds Pydantic request and response models with field and cross field validation. The services folder handles reservation rules, seat assignment checks, status transitions, and staff management. The models folder holds SQLAlchemy mappings and relationships. The dependencies folder handles current user resolution, scope enforcement, and database session injection. The core folder handles configuration, token handling, password hashing, and common exceptions. The repositories folder is optional and is only used when it improves readability.

The frontend pages are split into public pages like login and customer registration, shared pages like profile and unauthorized or not found pages, customer pages like availability search and my reservations, staff pages like operational reservation list and status update, and manager pages like dashboard summary and seat management.

# Data Design
The database has four main entities. The first is users. A user has an ID, a full name, a normalized email, a password hash, a role, an active flag, and timestamps. The email must be unique. The role is customer, staff, or manager. The password is never stored as plain text.

The second entity is seats. A seat has an ID, a seat code, a capacity, an optional description, an active flag, and timestamps. The seat code must be unique. The capacity is between one and twenty. Inactive seats cannot be booked.

The third entity is reservations. A reservation has an ID, a customer ID, a seat ID, start and end timestamps, a party size, a food preference, an allergy declaration, optional allergy details, a status, and timestamps. Every reference must exist. The end time must come after the start time. The party must fit the seat. The status is one of four allowed values which are confirmed, seated, completed, or cancelled.

The fourth entity is restaurant settings. It has opening hours, duration, slot interval, minimum lead time, advance booking window, change cutoff, and time zone. The values are validated, and new settings apply to later bookings.

I use primary keys, foreign keys, unique constraints, and check constraints. I add indexes for common searches by customer, seat, start time, and status. I use a database transaction and a concurrency safe constraint to prevent double booking. I store timestamps in a consistent way and use the restaurant time zone for opening hours and daily staff lists.

The best way to prevent double booking in PostgreSQL is an exclusion constraint. This stops overlapping time ranges for the same seat for blocking statuses. I build a range from the start and end times using half open intervals so a reservation ending at two o'clock does not conflict with one starting at two o'clock. PostgreSQL usually needs the btree gist extension to combine equality on the seat with range overlap. If an exclusion constraint is violated, I return HTTP 409 as a booking conflict. A transaction alone does not stop every race, so the constraint is the real protection.

Allergy details are sensitive personal information. I collect only what is needed, limit access to the customer and authorized staff and managers, avoid putting allergy details in logs, and do not include them in broad reports. I also define a retention policy appropriate for a course project.

# REST API Design
All endpoints use the slash api slash v1 prefix and JSON request and response bodies. Protected routes need a valid access token and the right scope plus any resource level checks. There is a public endpoint to register a customer account and it returns 201. There is a public endpoint to log in and it returns 200. There is an authenticated endpoint to read the current profile and it returns 200. There is an endpoint to list active seats with the seats read scope and it returns 200. There is an endpoint to search availability with the seats read scope and it returns 200. There is an endpoint to create a seat with the seats manage scope and it returns 201. There is an endpoint to update a seat with the seats manage scope and it returns 200. There is an endpoint to read restaurant settings with the settings read scope and it returns 200. There is an endpoint to update settings with the settings manage scope and it returns 200. There is an endpoint to create a reservation with the reservations create own scope and it returns 201. There is an endpoint to list own reservations with the reservations read own scope and it returns 200. There is an endpoint to read one reservation with the right role or scope plus ownership and it returns 200. There is an endpoint to edit an eligible own booking with the reservations update own scope and it returns 200. There is an endpoint to cancel an eligible confirmed booking with own or operational permission and it returns 200. There is an endpoint to update an allowed status with the reservations update operational scope and it returns 200. There is an endpoint to list today's operational bookings with the reservations read operational scope and it returns 200. There is an endpoint to list and filter all bookings with the reservations read all scope and it returns 200. There is an endpoint to create a staff account with the staff manage scope and it returns 201. There is an endpoint to list staff accounts with the staff manage scope and it returns 200. There is an endpoint to update activate or deactivate staff with the staff manage scope and it returns 200. There is an endpoint to read date range counts with the reports read scope and it returns 200. There is a public health check endpoint that returns 200.

When a customer creates a reservation, they send a seat ID, a start time, a party size, a food preference, an allergy declaration, and optional allergy details. They do not send the end time because the backend calculates it. The success response includes the reservation ID, the seat ID, the start and end times, the party size, the food preference, the allergy declaration, the allergy details, and the status which is confirmed. I must choose one consistent way to format timestamps and stick with it.

Error responses use a consistent JSON structure with a code, a message, and optional details. A 400 means a malformed request or invalid business operation. A 401 means missing, invalid, or expired credentials. A 403 means the user is signed in but does not have permission. A 404 means the item was not found, and it may also be used to hide another user's resource. A 409 means a seat or time conflict or an incompatible state change. A 422 means the request schema or field validation failed. A 429 means the rate limit was reached. A 500 means an unexpected server error, and I never return stack traces or secrets.

Some API behavior notes are to use pagination for large lists, filter customer reservation lists by the authenticated user ID on the server, never accept a role or customer ID from a customer request as authority, use explicit response schemas and omit password hashes and secrets and unrelated private data, and document cancellation and status transition behavior in the OpenAPI descriptions.

# Authentication and Authorization
The authentication flow starts when a user submits their email and password in the frontend. The frontend sends a login request to the backend. The backend finds the active user by normalized email, verifies the password hash, and returns a short lived access token plus a safe user profile. The frontend then sends protected requests with the bearer token in the authorization header. The backend verifies the signature and expiry and the relevant claims, resolves the user and scopes and role and resource access, and returns either an authorized response or a 401 or 403 error.

For token design, I use a maintained JWT library and a strong secret or asymmetric signing key stored outside source control. I include only necessary claims like the subject which is the user ID, the expiry, the issued at time, and the scopes or role if the design uses token claims. I validate the signature, the expiry, and the relevant issuer and audience claims. I use short lived access tokens. Refresh tokens are optional for the MVP. I never put tokens in URLs or logs. I choose the token storage deliberately. I prefer in memory access token storage for a simple single page app or secure HttpOnly cookies with appropriate CSRF defenses, and I do not casually store long lived tokens in local storage. On a 401 error, I clear the invalid client authentication state and send the user back to the login page.

For password handling, I hash passwords using Argon2id or bcrypt with a maintained library and an appropriate work factor. I never store or log plain text passwords. I use generic login failure messages to reduce account enumeration. I apply reasonable password length rules and login throttling where feasible.

The RBAC matrix shows what each role can do. A customer can register a public account as a customer only. They can view seat availability, create their own reservations, read their own reservations, and cancel their own eligible reservations. They cannot read operational reservations, update status, manage seats, manage staff accounts, manage restaurant settings, or read summary reports. A staff member can view seat availability if needed, read operational reservations, update reservation status with allowed transitions, and cancel reservations on a guest's behalf. They cannot register a public account, create their own reservations by default, read all reservations, manage seats, manage staff accounts, manage settings, or read summary reports. A manager can do almost everything including reading all reservations, managing seats, managing staff accounts, managing restaurant settings, and reading summary reports. They cannot create or promote other managers through the app.

The scope mapping shows which scope goes with which role and what extra check is needed. For example, the reservations read own scope is granted to customers and the extra check is that the reservation customer ID equals the current user ID. The reservations create own scope is granted to customers and the extra check is to ignore any client supplied customer ID and assign the current user. The reservations update own scope is granted to customers and the extra check includes ownership, editable status, cutoff policy, and rechecking availability. The reservations cancel own scope is granted to customers and the extra check includes ownership and cancellation policy. The reservations read operational scope is granted to staff and managers and the extra check is to limit the returned fields and use them only for operational purposes. The reservations update operational scope is granted to staff and managers and the extra check is to validate the allowed state transition. The reservations read all scope is granted to managers and the extra check is manager permission plus auditing important actions. The seats read scope is granted to authenticated roles as needed and the extra check is to expose only suitable public or operational fields. The seats manage scope is granted to managers and the extra check is to validate capacity and deactivation rules. The staff manage scope is granted to managers and the extra check is to prevent self escalation and unauthorized manager assignment. The settings manage scope is granted to managers and the extra check is to validate operating hours and booking rules. The reports read scope is granted to managers and the extra check is to aggregate data and omit unnecessary personal details.

In FastAPI, I enforce scopes using a dependency that checks the current user's scopes against the scopes required by the endpoint. If any scope is missing, it raises a 403 error. The service layer still enforces ownership or authorized operational access. This is illustrative pseudocode and not drop in code. The final dependency design must correctly integrate FastAPI's security scopes, current user resolution, and role to scope mapping. I must never let a caller submit their own scopes.

For ownership and privilege escalation, I derive the customer identity from the validated token and never from a user controlled customer ID field. I query customer owned records with both the reservation ID and the current user ID, or I perform an equivalent explicit ownership check. I return 403 or 404 consistently according to my documented resource disclosure policy. Only a manager authorized service can create staff accounts or assign staff roles. I never allow a user to update their own role through profile endpoints. I audit manager actions like staff activation, seat changes, and status overrides.

# Reservation and Seat Availability Logic
For availability search, I validate the requested start time, duration, party size, and restaurant operating hours. I select active seats whose capacity is at least the party size. I exclude seats with a blocking reservation that overlaps the requested interval. I return eligible seats with the minimal information needed for selection. I treat the results as a snapshot only and recheck availability during reservation creation.

For reservation creation, I authenticate the customer and require the reservations create own scope. I validate that the seat exists, is active, and has enough capacity. I validate the time range, operating hours, booking lead time, and allowed duration. I create the reservation in a database transaction. I let the database exclusion constraint or chosen concurrency safe mechanism reject overlaps. I commit on success and convert known conflict violations to HTTP 409. I return the persisted reservation data transfer object.

The status transitions are confirmed to seated to completed, and confirmed can also become cancelled. The team must decide whether staff confirmation is required, whether customers can cancel after seating, and whether managers can override a transition. I enforce the finalized transition matrix in the service layer, not just in the UI.

For edit and cancel behavior, an edit that changes the seat or time must re run all availability and capacity checks. Cancelled reservations should no longer block a seat, consistent with the database exclusion predicate. Cancellation should be idempotent or return a documented conflict for an already cancelled booking. I define a cancellation cutoff and test it at the API level. I do not silently reassign a reservation to another seat unless that behavior is explicitly included in the requirements.

# Frontend and Backend Integration
I centralize API calls in the frontend source API folder. I use typed request and response interfaces aligned with the backend Pydantic schemas. I configure one base URL using environment configuration. I handle loading, validation errors, unauthorized responses, forbidden responses, and network failures consistently.

React route guards improve navigation by hiding pages from users without the relevant role. They are not a substitute for backend authorization. A user can call the API directly, so every protected endpoint must enforce scopes and resource level permissions.

The suggested UI states include a loading state while availability or reservations are fetched, an empty state when no seats or reservations match the query, inline field errors for invalid date or time or party size or allergy details, a conflict message when a seat becomes unavailable during booking, a confirmation screen after successful reservation creation, unauthorized or forbidden screens for 401 and 403 responses, and accessible labels and keyboard navigation for forms and tables.

I keep frontend types synchronized with the API contract. Generating TypeScript types from OpenAPI later is nice to have, but manual types are acceptable for a small MVP if reviewed carefully.

# Security and Privacy
For transport security, I use HTTPS in deployed environments and never send credentials over plain HTTP. For secrets, I load signing keys and database credentials from environment variables or a secrets manager and commit only placeholders in the environment example file. For password security, I use Argon2id or bcrypt and never log passwords. For authorization, I apply backend scope checks, role rules, and object level ownership checks. For SQL injection, I use SQLAlchemy parameterized queries and avoid building SQL from untrusted strings. For XSS, I render user text safely and do not use unsafe HTML injection without sanitization and justification. For CSRF, if authentication uses cookies, I use appropriate SameSite, Secure, and HttpOnly flags plus CSRF defenses. Bearer headers have a different CSRF profile but still require XSS aware token handling. For CORS, I allow only known frontend origins and do not combine wildcard origins with credentialed requests. For rate limiting, I apply reasonable limits to login and registration if feasible. For data minimization, I collect only required customer details and restrict allergy information and avoid it in logs. For error messages, I do not expose stack traces, database credentials, tokens, or internal implementation details. For auditability, I record important manager actions without storing unnecessary sensitive payloads.

Allergy details are customer declared and can be operationally important. I limit access to the customer and authorized staff and managers who need the information. I do not place details in URLs, analytics, broad exports, or routine logs. I clearly communicate that SitNeat records declarations and does not guarantee allergen free food. I also define a simple retention policy for how long completed and cancelled reservations are kept and how customer account deletion or deactivation is handled. I avoid collecting unnecessary personal information.

# Error Handling and Observability
For error design, I use a consistent error response containing a stable machine readable code, a safe human readable message, and optional field details. I map known validation, authorization, missing resource, and conflict exceptions to appropriate HTTP statuses. Unexpected exceptions are logged server side with a correlation or request ID and returned as a generic 500 response.

For logging, I log the request ID, route, status code, duration, and relevant non sensitive event metadata. I do not log passwords, bearer tokens, database URLs, or full allergy details. I log security relevant administrative actions with the actor ID, action, target ID, and timestamp. I keep local development logs useful without exposing secrets.

I provide a lightweight health endpoint for deployment checks if needed. I do not expose database diagnostics or sensitive configuration through public health responses.

# Testing Strategy
My testing strategy covers several layers. Unit tests check time validation, status transitions, scope mapping, and booking policy using Pytest. API integration tests check register and login, create reservation, list own bookings, and manager operations using FastAPI TestClient or HTTPX with Pytest. Database integration tests check foreign keys, constraints, exclusion constraints, and transaction rollback against a PostgreSQL test database. Authorization tests check that a customer cannot read another user's reservation, that staff cannot manage staff, and that manager only routes are blocked for customers using Pytest. Concurrency tests check that two overlapping attempts for the same seat result in only one success using concurrent integration requests. Frontend tests check form validation, loading and empty and error states, and role specific navigation using Vitest and React Testing Library. End to end tests check that a customer books, staff updates status, and a manager creates a seat using Playwright optionally.

The minimum acceptance test scenarios are that public registration always creates a customer even if the request includes a role field, that correct credentials issue a token and incorrect credentials do not, that an expired or invalid token cannot access protected endpoints, that a customer cannot retrieve update or cancel another customer's reservation, that a staff user cannot create or deactivate staff accounts, that a manager can manage seats and staff within the documented policy, that a party size above seat capacity is rejected, that inactive seats cannot be booked, that two overlapping reservations cannot occupy the same seat, that cancelled reservations release the seat according to the chosen conflict rule, that invalid allergy declaration combinations are rejected, that illegal reservation status transitions are rejected, and that API error responses do not expose stack traces or secrets.

For test data, I use synthetic test users and allergy examples only. I never copy real customer credentials or sensitive data into the repository. Tests involving PostgreSQL exclusion constraints should run against PostgreSQL rather than relying only on SQLite.

# Configuration Migration and Deployment
For environment configuration, I keep placeholders in an environment example file. The variables include the app environment, a secret key, the database URL, the access token expire minutes, the frontend origin, and the restaurant time zone. I never commit a real environment file. I validate required configuration at application startup and fail safely if critical secrets are missing.

For database migrations, I create SQLAlchemy models and the initial Alembic migration. I review the generated migration SQL before applying it. I add PostgreSQL extensions and exclusion constraints through explicit migrations. I run migrations in development and test environments. I back up data before production schema changes if a deployed environment contains important data.

For deployment, I deploy the frontend as a static web application and the FastAPI backend as an application service. I use a managed PostgreSQL database or a properly maintained PostgreSQL instance. I configure production CORS to the exact frontend origin. I set environment variables through the hosting platform's secret management. I use HTTPS, run migrations as a controlled deployment step, and create a basic readme with setup instructions. I keep logs free of secrets and test the deployed API's authentication and authorization behavior.

For local development, a student friendly setup can run PostgreSQL locally, start FastAPI with a development server, and run the React development server separately. The readme should document prerequisites, environment setup, migrations, seed data, tests, and start commands.

# Risks and Trade-offs
There are several risks. A double booking race could make two customers believe they reserved one seat. I mitigate this with a PostgreSQL exclusion constraint or a proven locking strategy and test concurrent attempts. Inconsistent role enforcement could allow unauthorized administrative access. I mitigate this with central scope dependencies, ownership checks, and negative authorization tests. Scope creep could stop me from finishing on time. I mitigate this by freezing the MVP and deferring payments, delivery, AI, and multi branch features. Token theft or poor storage could compromise an account. I mitigate this with short expiry, a deliberate storage strategy, HTTPS, XSS defenses, and no token logs. Allergy information exposure is a privacy and operational risk. I mitigate this with data minimization, restricted endpoints, safe logs, and limited report fields. Time zone confusion could produce incorrect availability results. I mitigate this with timezone aware timestamps, one restaurant timezone, and an explicit serialization policy. Documentation drift could make the PRD, SRS, and TDD contradict the implementation. I mitigate this with stable IDs, API contract review, and a consistency checklist in pull requests.
